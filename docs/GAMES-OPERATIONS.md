# Games platform: operations, privacy and quotas

**Prepared and checked:** 2026-09-29 (America/Toronto). Cloudflare docs last-updated dates vary by page; recheck the official plan pages before deployment because quotas can change. The Games feature reuses the existing Cloudflare D1/KV resources and adds one SQLite-backed Durable Object class on Workers Free; it has no third-party service, paid API, or new secret dependency.

## Architecture and current capabilities

- `/games/` is the catalog and optional player/save/room surface; central metadata and stable IDs live in `src/data/games.ts`. Existing mini-games stay in `src/components/lab/` and `/lab/`; the Games cards link to those canonical implementations. No game was created or copied.
- Existing Lab game sections for Minesweeper, Memory Pairs, Isometric Stack, Bubble Pop, and Reaction Timer use a tiny shared tracker from `src/scripts/game-runtime.ts`. The shared client checks for `[data-lab-experiment]` and dynamically imports that module only on Lab pages; unrelated pages do not request the game-tracking chunk. This adds no gameplay or copied implementations.
- `mountGameLifecycle(root, module)` is the future game adapter: it waits until visible/in-view, initializes once, pauses/resumes on visibility/intersection, supplies capability facts and reduced-motion preference, then destroys owned resources. It creates no rendering loop. Game modules own state, presentation, preferences, audio, and their own controls.
- `mountGameSession(root, gameId)` records one anonymous run ID per mounted tab/game instance, sends a start/end beacon and at-most-minute heartbeats while visible/in-view. It counts only intervals after user input, stops accumulation after two idle minutes, and sends no keypress, pointer coordinates, score claim, or game-state payload. Offscreen/hidden pauses close the row; returning reopens that tab's row. Concurrent tabs get distinct run IDs. `IntersectionObserver` absence degrades to viewport-visible behavior.
- Capability detection is opt-in when a future game mounts. Canvas 2D/WebGL2 contexts are checked separately (the probe WebGL context is released); WebGPU, Web Audio, gamepad, pointer/touch and reduced motion are feature-detected. A physical keyboard is not reliably detectable, so the field means keyboard event support, not proof of a connected keyboard. Future games must offer semantic controls and usable touch/pointer alternatives where appropriate; audio must remain optional and start only after an appropriate user action.
- `src/components/GameShell.astro` is the reusable, game-agnostic page chrome. It takes `gameId`, `title`, `instructions`, optional `level` (1–3) and `initialState` (`loading`, `ready`, `paused`, `error`, `results`); game markup goes in the default slot and optional result details in `slot="results"`. It follows the site container/glass tokens and defaults to server-rendered `ready`, so its instructions and game-owned fallback remain available with JavaScript disabled. Consumers should not server-render a transient loading/paused state unless they also provide an intentional no-script fallback.
- `src/scripts/game-shell.ts` exports `setGameShellState(root, state, { message?, focus? })` and binds native-button pause/resume controls. State text is announced via one atomic status live region (`polite` for ordinary changes, `assertive`/`alert` on error). Error/results headings receive focus; pause/resume move focus to the newly available counterpart. The shell emits `bnji:game-pause` / `bnji:game-resume`; `mountGameLifecycle` listens to these and keeps its visibility/intersection pause gates in force. Hiding a tab/offscreen game pauses it without stealing focus; terminal results pause the game handle. Keep game rules and visual content in the game module/slot, not this shell.
- Device/IP and session data is in private D1 tables and visible only through `/admin`'s existing session/bearer guard. The public leaderboards select only `displayName`, `score`, `tieBreak`, and `achievedAt` from validated rows. Tracking failures return an empty `204` beacon and do not block play.
- One optional global player identity is available from `/games/`; a 160-bit random, case-insensitive recovery code is shown once and only its SHA-256 digest is stored. No email, password, third-party identity, owner reset or recovery secret is required. Signed-in sessions are random 256-bit opaque tokens, stored as digests in D1 and sent only in Secure/HttpOnly/SameSite cookies. Login failures are throttled/locked for 15 minutes after 8 failures per IP hash; account creation is bounded to 8 attempts per 15 minutes/IP. Local API tests exercised the lock threshold, `Retry-After`, hashed-only persistence, lock expiry, and confirmed changing guest cookies, User-Agent, or `X-Forwarded-For` does not reset the bucket. In deployed Worker traffic, `CF-Connecting-IP` is supplied/overwritten by Cloudflare's edge; direct local requests can set that header and therefore do not independently prove edge anti-spoofing. The throttle is per source IP: a shared NAT can experience a temporary 15-minute lock, but repeated requests cannot extend an active lock, and a successful login clears that IP's failure row. A distributed attacker can spread attempts across source IPs; the 160-bit random recovery credential is the primary defense against guessing. A player can rotate the recovery code (revoking other devices), sign out, export profile/saves/scores, or delete the cloud account. Losing both the code and every live session is unrecoverable.
- Account creation/sign-in claims only the current validated `bnji_ps` guest session's previously unlinked game rows. Existing localStack/Memory Pairs bests are copied into IndexedDB as local progress snapshots, never treated as verified scores; guest play/local progress work without accounts. The server save contract is stable catalog game ID + slot ID + positive schema version + bounded JSON blob + revision/update time. Per player: max 25 slots × 16 KiB each; API uses compare-and-swap revisions, returns current data in `409`, and never silently picks a winner. The browser stores pending saves in IndexedDB, retries transient/network failures up to three attempts with backoff, preserves pending local data offline, and asks the player to choose cloud or device data on conflicts. Migration registry is a generic hook; no game-specific data migration is claimed.
- Generic rooms use one SQLite-backed `GameRoom` Durable Object per 128-bit unguessable code, reached only through same-origin Worker routes that derive the principal from `player-context`; clients cannot assert member IDs. Hibernation WebSockets carry a version-1 JSON state envelope, ≤4 KiB/message and ≤3 KiB/state, 8 connected/reserved members, one persisted state write/5 seconds/room, 2-minute reconnect grace, and 2-hour absolute expiry; inbound traffic is bounded by a pre-parse 8-frames/second-per-connection abuse ceiling (close 1013) plus, for chat, a soft per-member token bucket (chat plan Phase B). CAS conflicts return a current snapshot; protocol/member/rate/size checks are server-enforced. Room state is opaque and untrusted: the service does not validate turns, moves, score or game rules. The `/games/` panel is a transport smoke surface, not a playable game.
  **Room chat: implemented (chat plan Phase B, 2026-09-30); admin-visible moderation tooling: planned.** In-room chat carries guest/account display names (gateway-resolved, `Player`/`Guest` fallback), is ephemeral by design — it lives inside the room's 2-hour lifetime, survives reconnects as bounded history, and is deleted with the room by the existing `alarm()` (chat, moderation log and mute tables all go). It is stored in the room's own Durable Object SQLite (never KV, never D1 per message): `game_room_chat` (200-row trim), `game_room_chat_log` (host actions), `game_room_mutes` (principal-scoped, reconnect-proof). The rate model changed from the old 1 msg/s socket ceiling to a pre-parse global abuse ceiling (8 frames/s/connection, close 1013) plus a per-member token bucket (burst 5, refill 4 s) held in the socket attachment, because a typing burst must not close the connection. The host can remove messages (tombstones), kick (close 4003, rejoin allowed) and mute; kick/mute/limits are refused softly (`chat_rejected`), never by closing an innocent socket. Moderator visibility for *administrators* requires a bounded D1 room registry so administrators can list and read active rooms; that is a deliberate trade (a D1 compromise would expose unguessable, 2-hour, 8-seat room codes) and it is documented in `docs/CHAT-SYSTEM-PLAN.md` §6.1 — it arrives with Phase C, along with reporting. Design, schema and quota math: [`CHAT-SYSTEM-PLAN.md`](./CHAT-SYSTEM-PLAN.md); collection rules: [`DATA-COLLECTION-POLICY.md`](./DATA-COLLECTION-POLICY.md).

## Storage and score trust

`migrations/0011_games.sql` adds `game_sessions` and `game_scores`; `migrations/0012_game_players_saves.sql` adds `game_players`, digested `game_player_sessions`, hashed-IP `game_auth_attempts`, and bounded JSON `game_saves` to the existing D1 database bound as `BOARD_DB`. `migrations/0013_names.sql` (chat plan Phase A) adds the `guest_profiles` table (display name keyed by `sha256(session id)`, fixed 30-day sweep) and the nullable unique `handle`/`handle_changed_at` columns on `game_players`. `migrations/0014_chat_moderation.sql` (chat plan Phase C) adds `room_registry`, `chat_reports`, `chat_reporters`, `chat_moderation_log` and `chat_bans`. No new D1 database is needed. `wrangler.json` also binds one new SQLite-backed Durable Object class (`GAME_ROOMS` → `GameRoom`) through the Worker `game-rooms-v1` class migration; it uses no additional secret beyond the existing `ACCESS_SECRET` (Phase C derives the DO admin service token from it — already provisioned for `/admin` sessions, passed to the class as a top-level Wrangler secret).

- A game-session row stores anonymous `session_id`, per-tab `run_id`, reserved nullable `player_id`, stable `game_id`, start/end/last-seen timestamps, bounded active milliseconds, server-observed IP and user-agent, coarse browser/OS/device class, and client-reported screen/input class. `run_id` prevents two tabs sharing a guest cookie from racing one heartbeat row. SQL ensures a heartbeat updates at most once per 45 seconds and bounds each increment to the smaller of the client delta, 65 seconds, and elapsed server time. Hourly cleanup closes at most 50 stale unfinished runs per invocation after two idle minutes; a larger closure backlog drains across later triggers.
- Client-provided screen/input classes are allowlisted coarse labels, not proof of hardware. IP/UA come from the request, with Cloudflare's `CF-Connecting-IP` header as the production source. The system does not collect precise GPS, referrer, key/input details, score-game replay, or audio/video.
- Score rows keep stable game/mode, integer score, optional tie-break, server timestamp, anonymous `session_id`, nullable `player_id`, 1–24 code-point display name, validation state, and an idempotency key. One best score per anonymous session/game/mode is retained, and each game/mode keeps at most 500 validated rows. Both score rows and session rows are removed using the shared retention setting.
- `POST /api/games/scores` validates the bounded payload and rate-limits attempts, then requires a registered game-specific verifier in `src/server/score-verifiers.ts`. No verifier is registered in this part-one task. It therefore returns `503 {"error":"verifier_unavailable"}` before D1 insertion; an arbitrary client score can never appear as valid. A verified but non-best/out-of-top-500 result gets an explicit `202` response rather than a silent success. Replays are constrained by the D1 session/idempotency uniqueness plus each future verifier's run-proof logic.
- `GET /api/games/leaderboard?gameId=bnji.glass-minesweeper&mode=default&page=0` has a 25-row page, maximum page index 19 (500 stored rows/mode), indexed ordering, rate limits, and no internal IDs in successful row results. Missing/exhausted D1 returns `503 storage_unavailable`, not an invented empty leaderboard. Invalid IDs/modes/pages return `404`/`400`; rate limit returns `429`.

## Tracking retention and existing telemetry

The source-of-truth audit found a discrepancy: `security_events` had a fixed 60-day constant and a threshold-triggered lazy purge; the current admin settings did **not** actually offer the retention editor described in older documentation. This implementation closes that gap rather than building a parallel tracker:

- Adds `trackingRetentionDays` to the existing persisted `/admin` → **Configuration** editor (integer 1–365, default 60).
- Reuses the setting for new `game_sessions`/`game_scores`, existing private `security_events`, and private `board_paint_activity`; the existing board-report dedup table keeps its separate 60-day constant.
- Adds an hourly Cron Trigger that purges expired game sessions, scores, security events, and Paint activity using indexed timestamps. Each table gets a 50-row primary delete batch; only a full batch triggers one additional bounded 10-row catch-up batch, so at most 60 rows/table/sweep. Up to 50 stale game sessions can also be closed. Private admin reads perform a separate bounded recovery batch. Caps were reduced from part one to preserve shared D1 write headroom for accounts/saves. Ingest never waits for/depends on tracking storage.
- Public and admin read paths filter at the configured cutoff immediately. Physical deletion backlogs drain at up to 60 rows/table/hour under continuous backlog, plus scheduler jitter; Cron is not a precise TTL service, and there is no hard one-hour physical-deletion guarantee. The sweep logs a generic failure and resolves; leftover rows are retried on later hourly sweeps or relevant admin reads. If strict deletion at the exact cutoff is a legal requirement, this design would need a different storage product with row TTL or a tighter external policy decision.
- The maximum scheduled D1 query count is 14: retention-setting read, stale game-session close, expired player-session prune, auth-attempt prune, four primary deletes, at most four catch-up deletes, and the guest-profile purge plus its at-most-one catch-up. Each cleanup statement is independently bounded; catch-up statements run only when the primary batch returns all 50 rows. Values are 50 and 10, never looped until empty. Guest display names (`guest_profiles`) use a fixed 30-day window from `src/config/names.config.ts`, independent of `trackingRetentionDays`. Expired/revoked player sessions are pruned in batches of at most 50 per hourly sweep; hashed-IP authentication-attempt rows are also capped at 50 and use the same configurable `trackingRetentionDays` cutoff (the active rate-limit window remains 15 minutes). Saves/account data persist until explicit account deletion.
- Admin → **Games & play** shows aggregate totals and up to 100 recent run details: active minutes, validated score counts, IP, raw UA, and coarse device/browser/OS data. It does not expose player, guest-session, or per-run internal IDs. It is `no-store`, admin-only, and never included in the public leaderboard or public site pages.

Reused rather than duplicated: the existing D1 binding/migrations, KV-backed rate limiter, existing anonymous `bnji_ps` session cookie, existing `clientIp()` helper, existing DB-backed admin authentication and site-settings store. New session starts (which can create D1 rows) are limited to 30/minute/IP using the existing KV limiter. Heartbeats do not write KV: the D1 update is atomic and accepts at most one heartbeat per run per 45 seconds. KV has only 1,000 writes/day on Free, so this avoids spending that shared budget on the normal minute-heartbeat path. Missing/failing KV remains fail-open for gameplay and telemetry. The old security enrichment path remains separate for abuse triage; game tracking stores only the coarser game-specific dimensions above.

Account tables/saves share the existing `BOARD_DB` allowance with board/profile/security/Paint and Games telemetry; Durable Object SQLite is a separate service budget.

- [WebSocket hibernation API](https://developers.cloudflare.com/durable-objects/reference/websockets/): use `acceptWebSocket`/hibernation handlers; the Worker authenticates the player before proxying the upgrade to the private DO binding.

- [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/): UTC scheduling; the single hourly trigger uses one of the account's maximum five Free Cron Trigger slots. Confirm one is available.

No Workers Paid tier, third-party service, email/API credential, R2, Queue, or external scheduler is required by this design. **Amended 2026-09-30:** the account is still expected to run on the $0 Workers Free tier for these features, but the older absolute ban on paid products and bindings is lifted where a later feature genuinely needs one — see [`DEPENDENCY-POLICY.md`](./DEPENDENCY-POLICY.md) §6. Any such change is a separate owner decision with its cost recorded; it is not implied by this document. The planned chat and private-messaging work is designed to fit inside Free allowances, with R2 only proposed for image storage and only after its Workers Free binding availability is confirmed.

### Shared daily budget and safe operating envelope

At 100 daily players, each visible for two hours/day and playing one game at a time:

- Tracking emits about 12,000 minute heartbeats plus starts/ends; Cron adds 24 Worker invocations. Add account-page/API calls, room create/upgrade and ordinary site traffic to the shared 100,000 Worker-request/day budget.
- Heartbeats update about 12,000 D1 rows. With the `last_seen_at` indexes plus the base row, budget approximately 36,000 physical D1 row writes/day, before start/end/score and account/save writes. At 200 equally active players, that heartbeat path alone is about 72,000 writes/day.
- Retention is deliberately bounded lower than the part-one plan: each hour deletes at most 60 rows per table (50 primary + 10 catch-up), with up to 50 stale game-session closures, 50 expired/revoked player sessions and 50 aged auth-attempt records pruned. Using current indexes, a completely saturated hourly schedule is approximately 1,380 D1 writes/hour or 33,120/day (session cleanup 5 writes/row, scores 6, security 5, Paint 2, stale closes 1, player-session deletes up to 3, auth-attempt deletes about 2). Together with the 100-player heartbeat example, this is ~69,120 D1 row writes/day. The remainder—about 30,880/day—is a *ceiling estimate*, not a reserved account quota: account creation/claims, login windows, up to 25 save slots/player, site writes, indexes and measurement variance all consume it. A player repeatedly saving is also D1 write traffic. If aggregate `rows_written` trends toward 100,000/day, reduce traffic or pause optional save/room features while remaining on Free; do not assume the feature-only math can override the existing site's usage.
- The cleanup cap limits physical purge throughput to 60 rows/table/hour; read APIs hide expired rows immediately, but a large backlog may take many hours/days to physically drain. This trades deletion throughput for D1 write headroom. Monitor backlog and exact D1 `rows_written`/`rows_read` rather than raising caps automatically.
- DO SQLite usage is *not* included in the D1 totals above. A room allows at most 8 members, a pre-parse ceiling of 8 inbound frames/second/connection (chat plan Phase B replaced the former 1 msg/s rule; chat itself is additionally budgeted per member at burst 5 then ~15/min), at most one persisted state update per room/5 seconds, 4 KiB messages, 3 KiB state and two-hour hard expiry. At the protocol ceiling, eight continuously active members could send up to 460,800 inbound frames across a two-hour room; 20:1 accounting is about 23,040 DO requests plus upgrade/creation, below 100,000 for one such room. This is a deterministic request-count illustration, not a capacity promise: DO GB-s and SQLite row reads/writes/storage depend on actual events/room reuse and are shared with any other DOs in the account. Hibernating idle connections avoid idle duration charges. Check DO analytics (requests, GB-s, SQLite rows/storage) before inviting real traffic; this repository has only local smoke verification, not production telemetry.
- Shared KV Free allows 1,000 writes/day. Heartbeats/saves do not write KV; room creation uses the existing rate limiter and shares KV with all other features. Account lockout uses D1, not KV. Monitor Workers, D1, DO and KV separately.
- **Planned chat and private messaging (2026-09-30 plan).** Neither may add KV writes. Room chat spends DO SQLite row writes (200-row cap per room, trimmed on insert), while private messages spend D1 row writes (1 per message, plus reads and the retention purge). Worst-case room chat at the per-member budget is ≈14,400 DO row writes for a saturated 2-hour room; a DM-heavy day shares the same 100,000 D1 writes/day account-wide budget as tracking, accounts and saves. This is a planning estimate, not a reservation — watch `rows_written` for both D1 and DO after each phase ships, and use the kill switches in the chat plan (§14) rather than assuming headroom.

These are bounded planning estimates, **not** a quota reservation, SLO, or traffic guarantee. Cloudflare quotas are shared account-wide and reaching a Free ceiling can fail requests. Keep the site on Workers Free, monitor the service dashboards after launch, and lower request/write rates or disable optional rooms/saves before a ceiling is reached. The guest/local play path does not require accounts, saves, or rooms. Scores remain unavailable until a game-specific verifier is deliberately registered.

## Browser capability references (checked 2026-09-29)

- [Canvas 2D](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API): broadly available; canvas pixels need semantic/DOM equivalents for accessible controls and important content.
- [WebGL](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API): broadly available but still depends on usable device/GPU support; check and provide a non-WebGL path.
- [WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API): limited availability and secure-context constrained; strictly optional, never a baseline requirement.
- [Web Audio](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API): widely available, but audio contexts and playback must remain optional and user-controlled.
- [Gamepad](https://developer.mozilla.org/en-US/docs/Web/API/Gamepad_API): broadly available, but controller presence is optional; listen for connection and retain keyboard/touch/pointer input.
- [Intersection Observer](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API): broadly available and appropriate for suspending work without scroll polling. The client also respects `visibilitychange` and `prefers-reduced-motion`.

## Room moderation (chat plan Phase C)

The `/admin` panel gained a **Chat** tab (plan §6.2). What it can do, and what
each action means operationally:

| Panel / action | Effect | Notes |
| --- | --- | --- |
| Active rooms → **Open** | Streams the live transcript from the room's Durable Object over the service-authenticated `/admin/read` endpoint | Display view strips URLs when `filter.stripUrlsForAdmin` is on (stored text is untouched). Members list includes each principal hash. |
| Active rooms → **Close** | Closes every socket (`4002 Room closed by administrator`), deletes every room table, removes the registry row | Irreversible; the room code stops working immediately. |
| Transcript → **Delete** | Tombstones the message (`removed = 'admin'`, text blanked) and repaints every open client with `An administrator removed a message` | Logged in `chat_moderation_log`. |
| Transcript → **Ban** | Adds `chat_bans` row for `moderation.defaultBanMinutes` (editable per call, clamped to `maxBanMinutes`) and kicks any live session (`4003`) | Banned principals cannot rejoin (`403 chat_banned` at `/ws`). Ban survives reconnects until expiry or unban. |
| Transcript → **Kick** | Disconnects (`4003`) without banning; the principal can rejoin | Logged. |
| Reports → **Resolve / Dismiss** | Sets report status + optional note | Both keep the snapshot until the retention sweep. |
| Reports → **Ban author** | Escalation: bans the snapshot's `author_hash` and resolves the report | Works even after the room is gone — the snapshot is the evidence. |
| Active bans → **Unban** | Deletes the ban row | |
| Moderation log | Append-only audit: action, room code, hashes, detail | Hashed principals only; retained with the shared sweep (`trackingRetentionDays`). |

Reporting (plan §6.4): members see a **Report** button on other people's
messages; `POST /api/chat/report` asks the room to snapshot the message into
D1 before the room can expire. Limits: `moderation.reportMaxPerWindow` per
`reportWindowMs` per hashed IP, counted in D1 — a `429 rate_limited` is
expected under abuse, not an error. The §6.3 blocklist/filter is a triage aid;
empty by default; never describe it as protection.

Retention: `room_registry` (expired rows), aged `chat_reports`/`chat_reporters`
(> `trackingRetentionDays`), expired `chat_bans`, and aged
`chat_moderation_log` are swept by the same hourly Cron as the tracking tables
(budget: 19 DELETE statements per run). Account export includes a
`chatModeration` section; account deletion removes every row keyed to the
principal.
